# Expansion Review — 2026-10-20 (second)

**Brief dated:** 2026-09-10
**Last status review:** 2026-10-20 — [docs/reviews/2026-10-20-status-2.md](2026-10-20-status-2.md)
**Milestone that prompted this:** the service layer went live (launchd dashboard and refresh jobs, WAL, the shared chart template) and 9 of 13 criteria were verified against executed evidence. The brief's own wording was then audited against the code and three places where the brief no longer describes the thing it grades came out.

## Headline

The target should move in wording only. The objective, the constraints and the "is done" bar all still hold — what changed is that the brief was written before the code existed, and three of its sentences have since drifted away from what the code does. Two of those drifts are a test-count parenthetical and a metric list that no longer match reality; the third is a verification method that describes a mechanism the project deliberately chose not to build. None of these is a change of direction: the fix is to make the brief grade what the project actually does, and to record the one idea that was declined so it stops being re-asked.

One decision went the other way. Criterion 7 names no Garmin source, and the status review suggested naming one. It was left alone: the criterion is satisfiable as written now that the endpoint exists, and pinning the brief to an endpoint path would freeze an implementation detail that is free to change.

## What building this taught us

**Assumptions that turned out wrong:**

- That a criterion's verification method would describe the mechanism the project would actually build. Criterion 4 asked for the comparison list to be checked against "route/distance history"; the project built a grouping by the 80/20 plan workout code, because the activity names carry it and it is the cohort the user's training plan is written in. The verification method survived a change of mechanism and would have failed a correct implementation.
- That a metric list in a brief stays true as long as the metrics do. It does not: the Runalyze VDOT port added three shipped families on 2026-10-17, five weeks after the brief was written, and the list was never updated. The code was right and the brief was stale.
- That a parenthetical test count is a fact rather than a snapshot. Criterion 5's "(236 tests)" was correct for one month and wrong twice since (533, 596, now 598). A number that must be edited every time the suite grows is a liability, not a check.

**Harder than expected, and why:**

- Keeping the brief and the code in agreement was harder than keeping either alone. Every metric family, every CLI and every Garmin endpoint the app depends on is a fact the brief could state, and each one is a place the two can drift apart silently — nothing fails when the brief is wrong, the next status review just grades against a target nobody implemented.
- The metric spec and the shipped code drifted apart in the same way: `age_graded` ships and is displayed but appears nowhere in `docs/v2/metrics-spec.md`, and `metrics/effective_vo2max.py` is implemented, undocumented and inert. Criterion 5's verification ("metric definitions match `docs/v2/metrics-spec.md`") was therefore already failing before this review — the spec gap is pre-existing and is live work, not a brief question.

**Surprisingly easy, or came for free:**

- The comparison mechanism the project did build turned out to be exactly as complete as the plan-code story suggests — every activity carrying the selected activity's code, across every date in the store. Rewording criterion 4 needed no new work, only an accurate sentence.
- The Runalyze families were already documented in `docs/v2/metrics-spec.md` §2.4. The brief's metric list was the only place they were missing, so closing the gap was one line rather than a documentation pass.

## Emergent capabilities

- `chart_theme.py` now owns every colour, layout and Plotly config in the app, so the visual system is one edit away from every chart. That makes "restyle the dashboard" a one-file change, and it makes the brief's "one shared visual template" requirement something the code now enforces rather than merely asks for.
- The `metric_series` table is a complete, Garmin-derived history that the dashboard does not read from — it computes its view in memory from activities. That means a copy of the live database is a fully functional replica, which is what made every destructive-feeling probe in the last review safe to run against real data.
- The four backfill CLIs plus `refresh.py` mean any column added to the store can be repopulated from Garmin without a hand-written SQL repair, because the activity-list payload is the source of truth for most fields.

## Adjacent problems noticed

- `garminconnect==0.3.2` is pinned and its own HTTP layer stalls behind Cloudflare; `garmin_http.py` is the load-bearing workaround and the brief names neither the pin nor the constraint. Not this project's job to generalise — but the pin is invisible to anyone reading the brief.
- The `watchdog` dependency was a placeholder for a file-watching feature that was never built. It was declared, installed on every clean clone, and imported nowhere; it has been removed. The lesson generalises: a dependency in the manifest is a promise to the reader, and an unused one is a promise nothing keeps.

## Amendments made to the brief

- **Objective:** unchanged.
- **Criteria added:** none.
- **Criteria removed or replaced:** none removed. Two amended:
  - **Criterion 5** — the stale "(236 tests)" parenthetical dropped, and the Runalyze VDOT families (`vdot.shape`, `marathon.shape_pct`, `prognosis.*`) added to the metric list, so the set the criterion grades matches the set the app ships.
  - **Criterion 4** — the verification method now names the mechanism the project built (every other stored activity carrying the same 80/20 plan workout code) instead of route/distance similarity, which would have failed the correct implementation.
- **Criterion 7:** unchanged, deliberately — see the candidate calls.
- **Is-done bar:** unchanged.
- **Out of scope added:** route/distance-similarity grouping for comparison activities — because comparison groups by the 80/20 plan workout code parsed from the activity name, which is complete and correct; route/distance cohorts were parked on 2026-09-12 and are a different question from "show me the same workout again".

Two changes outside the brief's text, recorded here so the trail is complete: `watchdog>=4.0` was removed from `pyproject.toml` (declared, installed on every clean clone, imported nowhere), and the brief now names the Runalyze families that `docs/v2/metrics-spec.md` §2.4 already documents.
