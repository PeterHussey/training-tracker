## Looks done vs is done

- **Attacked and survived:** the refresh path (timed against a copy, real Garmin API); the chart renderers (seven degenerate activity shapes × two unit systems, plus a window sweep on 909 real activities); the comparison list (completeness against the store, plus three edge cases); the laps parser (real 23-lap payload plus five malformed variants); the CLI surface (unknown flags, empty store, offline mode); the credential failure paths (empty store vs seeded store); the clean-clone install; the scheduled refresh under a live dashboard; SQLite concurrency under a live refresh; the e2e report against live data.
- **Only ever watched to succeed:** the live browser session in which an open dashboard reflects a scheduled refresh (the 30s poll was verified at mechanism level only — `_store_changed` flips to True — but no browser ever watched the sidebar caption change); the "fresh login with no terminal open" half of criterion 10; the Garmin Connect side-by-side of the laps/splits; the chart rendering after the title/legend fix (the fix's own test was green, but nobody re-opened the browser afterwards).
- **Could not be probed:** the Garmin Connect UI comparison (criteria 2 and 7) — Garmin Connect is a web app, not an API, and driving it would need a browser session and a side-effecting login; criterion 10's post-logout/login state, since logging the owner out is not something a review may do.

## Debt

- **Unversioned SQLite schema.** `store.py:_migrate()` does in-place `ALTER TABLE` with no version table. `avg_cadence` was added on top of `event_type` by copying the same guess-the-schema pattern. Undoing it means writing a migration table and backfilling `user_version`; the cost of the next column is another hand-written ALTER plus a test that it is idempotent.
- **`ts_ms` is not persisted.** `store.load_activities()` cannot restore it, so SQLite-loaded activities always carry `ts_ms = 0`. That is why the date-vs-timestamp mismatch that crashed `pipeline.py` cannot reach the live dashboard — but the invariant is unenforced, and a future `ts_ms` column would change metric behaviour silently.
- **A stale test-count parenthetical in the brief.** It has now been wrong twice (236 → 533 → 596), so the number will be wrong again; it should be dropped, not updated.
- **Two unhandled credential paths** (`refresh.py`, `dashboard.py:2168`) — every other credential failure in the app is already converted into a one-line message, so the cost is a copy of an existing pattern, not new design.
- **`watchdog>=4.0`** stays in `pyproject.toml` — one line to remove, but it keeps installing a package on every clean clone and implies a file-watching feature that does not exist.
- **The metric spec lags the code**: `age_graded` (shipped, displayed, criterion 9) and `effective_vo2max` (implemented, undocumented, inert) are both absent from `docs/v2/metrics-spec.md`.

## Risk

- **The launchd refresh job will write a stack trace to `logs/refresh.err.log` the first time the Garmin token expires**, and nothing surfaces it — the job is scheduled, not watched. The owner would see a stale dashboard and no explanation. Likely: Garmin's token lifetime is months, so this fires a few times a year, and the failure is silent until someone opens the log.
- **The dashboard will hard-crash on startup when the tokenstore is missing or expired and the store already holds activities** (`dashboard.py:2168`). The service then simply does not come back, and `launchctl` will report the job as failed rather than as an auth problem. Likely: same trigger as above, but with a visible outage.
- **`main` is 13 commits ahead of `origin/main` and unpushed.** A machine failure or a bad clone loses the service layer, the WAL switch, the monthly fix and the laps work. Likely if anything goes wrong with the working copy.
- **The weekly/monthly bucket convention is now documented only in a caption and in code.** If a future refactor re-centres the buckets, nothing fails — the charts just quietly shift. Low likelihood, silent consequence.
- **The e2e report asserts a subset of the 68 metric families it prints.** A family that is present but wrong still passes. Medium likelihood, low visibility.
- **`garminconnect==0.3.2` remains pinned and its HTTP layer still stalls behind Cloudflare** — `garmin_http.py` is the workaround, and that dependency is load-bearing but named nowhere in the brief. Low likelihood (it is bypassed), high cost if the pin is ever removed.

## Pathway options

**Now** — fix or stabilize what exists:

- Convert the two credential tracebacks into one-line messages: wrap `refresh.py`'s gateway construction and `dashboard.py:2168` the way the refresh button already is, so an expired token is a message in the log, not a stack trace.
- Document `age_graded` in `docs/v2/metrics-spec.md` (it ships, it is displayed, it is criterion 9) and either document or delete `metrics/effective_vo2max.py`, which currently emits nothing.
- Push `main` to `origin` — 13 commits of the service layer, the WAL switch, the monthly fix and the laps work are unpushed.
- Restart the dashboard and re-open the browser once, to confirm the title/legend fix (`72ba3a0`) reads correctly in every tab; nobody has looked at the rendered charts since that fix.

**Next** — highest-leverage addition given the current architecture:

- A `health_check.py` that runs the probes from this review — refresh against a copy, stored-vs-Garmin spot check, SQLite concurrency — as a scheduled launchd job, so the next review starts from a known baseline instead of rediscovering it. The probe scripts used here were scratch files outside the repo and would have to be rewritten.

**Later** — needs an architecture decision first:

- SQLite schema versioning (`PRAGMA user_version` plus an ordered migration list) — the third column added by guess-and-check, and the cost is now visible in the migration code.
- Persisting `ts_ms` (or making the calendar-day/timestamp invariant explicit) so the metric engine's day-window semantics stop depending on a column that silently is not stored.
- Deciding what the comparison mechanism should group by — plan codes are complete and correct, but the brief's wording still promises route/distance history.

**Alternative direction** — a pivot worth naming, if one is genuinely on the table:

- Freeze feature work for one cycle and spend it on making the service layer boring: a health check, a restart-on-failure policy for the dashboard job, and credential-error handling — accepting a smaller feature surface in exchange for a dashboard that can be left running unattended.
