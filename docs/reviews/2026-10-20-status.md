- **Attacked and survived:** live refresh under the 90s cap; live data validity (stored vs Garmin, 9/9 exact); the full test suite (533); the e2e report; both backfill CLIs including the write path against a sabotaged row; missing-credential error handling; SQLite concurrency under the code's real read/write patterns; best-mile and WMA rendering; comparison-group completeness and ordering against a SQL cross-check
- **Only ever watched to succeed:** the 13 chart renderers as *individual* charts — I probed the date window across them, but never attacked a chart with a degenerate series (all-zero, single point, extreme outlier) or with unit switching (metric ↔ miles); the e2e report's per-metric check coverage (it reports 68 families, but only asserts a subset); the refresh's behaviour when Garmin returns an empty list or a partial payload
- **Could not be probed:** criteria 10 and 11 were not probed by *running* the service, because no service exists to run — the evidence is absence (`launchctl list`, no plist, no `.streamlit/`), not a failed run. Criterion 7's laps/splits cannot be probed at all from the current Garmin endpoint: the payload does not carry them, so there is nothing to compare against Garmin Connect. The `--apply` path of the backfills was probed only against a **copy** of the real DB; I did not write to the real `data/training.sqlite`.

## Debt

- **Monthly aggregation is wrong by construction** — `resample_agg` labels monthly buckets at month end while `window_series` keeps buckets whose label is `<= until`, so the current month is always dropped. Every month that is not yet over will be missing. Undoing it means choosing a convention (label at month *start*, or keep the in-progress bucket explicitly) and touching `metrics/volume.py` + `session.py:window_series` + their tests.
- **Unversioned SQLite schema** — `store.py:_migrate()` does in-place `ALTER TABLE` with no schema version table. Every future column change means writing a migration that guesses which rows already have it. (Parked in the 2026-10-20 expansion review, but the cost is already paid in the code.)
- **Rollback-journal SQLite with no `busy_timeout`** — `journal_mode=delete`, no busy timeout, no WAL. Concurrency is safe today only because the code's read pattern is `fetchall`. The moment a reader holds a transaction open, the writer fails with "database is locked".
- **No `config.toml`, no shared chart helper, 12 inline hex literals, 16 hand-tuned `update_layout` calls** — the visual layer is copy-paste. Criterion 13 will need a real refactor, not a find-and-replace.
- **`watchdog>=4.0` is a declared dependency that nothing imports** — dead weight in the install, and a false signal that file-watching is a feature.
- **The README omits the install step** and `uv sync` does not install the dev extra, so the documented quickstart cannot succeed on a fresh clone. Every future contributor hits this first.
- **The brief's "236 tests" parenthetical is stale** (533 now) and criterion 7's verification method assumes a Garmin payload the endpoint does not return.

## Risk

- **The dashboard is currently reachable on all interfaces.** No `.streamlit/config.toml` means `server.address` is unset, so Streamlit binds `0.0.0.0`. On a laptop that is on a café or office network, the dashboard — which renders personal health and location data — is reachable by anyone on the same network. This is the most concrete risk in the project, and it is a one-line config fix that criterion 13 happens to cover.
- **Adopting launchd as a service without first fixing the SQLite concurrency story** risks the exact failure criterion 12 was written to prevent: a scheduled refresh writing while the dashboard holds a read transaction produces "database is locked" in the middle of a user-facing page.
- **Building the refresh job before the monthly-aggregation fix** would institutionalise the current-month gap into a scheduled, silent data loss: the live store is already missing October, and a nightly job would keep it that way without anyone noticing.
- **A 5-week review gap on a 41-commit project.** The last status review predates the Runalyze VDOT port, the whole service-layer criterion set, and a metric-family expansion; the 2026-09-10 review graded 2 of 6 criteria. The drift was invisible until today.
- **The metric layer is trusted, but the e2e report is the only end-to-end guard and it asserts a subset** of the 68 families it prints. A family that is present but wrong can pass.
- **Garmin API surface dependency** — `garminconnect==0.3.2` is pinned and `garmin_http.py` exists because the library's HTTP layer stalls behind Cloudflare. That workaround is load-bearing and undocumented as a constraint anywhere in the brief.
