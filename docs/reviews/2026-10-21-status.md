## Headline

Every one of the 13 criteria now has executed evidence behind it, up from 9
green / 4 yellow at the last review. The three criteria that were yellow have
moved for different reasons: criterion 4 was reworded by the expansion review
to the mechanism the project actually builds, criterion 5's spec gap was

sidebar instead of only in a log file nobody reads.

eyeball comparison against the Garmin Connect UI (criteria 2 and 7) and the

## Looks done vs is done

- **Attacked and survived:** the credential paths (empty `HOME`, every CLI and
  both dashboard states); the window boundary (mid-month, a month with no
  activity, a window inside one month); degenerate activity data across every
  chart; malformed Garmin payloads; SQLite concurrency (writer held open,
  four concurrent readers); a clean clone; repeated scheduled runs.
- **Only ever watched to succeed:** the e2e report's conditional metric
  families (`load.lt_hr`, `load.lt_pace` and their `best20`/`best30` variants
  report "no rows" against the live store — the payload is Garmin's and the
  chart says so rather than inventing a value, but it has never had a row to
  draw).
- **Could not be probed:** the Garmin Connect UI comparison for criteria 2
  and 7 — an API-to-API comparison against Garmin's own payloads was run
  instead, but nobody looked at Connect's screens next to the dashboard; the
  "after a fresh login" clause of criterion 10 — probing it needs a login
  cycle, and no probe was run that logs out or reboots.

## Debt

- **The activity's calendar day and its timestamp can disagree.**
  `metrics/vdot_shape.py` keys the shape series by `a.date`, while
  `pipeline._qualifying_window_days` matches days by `a.ts_ms`. After travel
  the two disagree and the shape series silently loses days. The crash is
  guarded (`1847734`), but the metric quietly under-reports. Undoing it means
  either persisting `ts_ms` as a column or changing the estimator's day
  definition — the latter is a metric change, not a bugfix.
- **Schema migrations are guesses, not versions.** `store._migrate()` adds
  columns by inspecting `PRAGMA table_info`; `avg_cadence` was added on top of
  `event_type` the same way. Undoing it means introducing `PRAGMA
  user_version` and a migration list.
- **`docs/v2/garmin-field-mapping.md` points at a path that no longer
  exists** (`v2/garmin_fields.py`; the registry is at the repo root). It is a
  generated document, so it was left alone rather than hand-edited.
- **The metric spec's registry list (§8) is Garmin-field-derived, not
  "every stored family"** — `age_graded` and `injury` are stored families with
  no registry key. Deliberate, but the section reads as more absolute than it
  is.

## Risk

- **The Garmin token can expire overnight.** The refresh and the health check
  both depend on it. The dashboard now shows the health check's verdict, so
  the failure is visible — but only after the app reruns, and the verdict is
  only as fresh as the last run.
- **`logs/health.log` grows without bound.** launchd appends; nothing rotates
  it. At ~10 lines per day it is trivial for years, but it is unbounded in
  principle.
- **A single-store, single-user design.** `data/training.sqlite` has no
  backup and no schema version, so a bad migration on a future column is
  unrecoverable without a copy of the file.
- **The chart template's shared layout is unverified against unusual data.**
  The degenerate attack covers values, not figure sizes — a chart with a long
  legend at a narrow width could still collide with the title the way it did
  before `72ba3a0`.

## Scope drift

- **Crept in despite being out of scope:** nothing found. The health check,
  the chart helper, the per-thread SQLite connections and the credential
  guards all serve criteria in the brief.
- **Built without ever being decided:** `metrics/effective_vo2max.py` was
  written as an estimator module and left undocumented for weeks; it is now
  named in the spec as the derivation path under `vdot.shape`, so it is
  decided rather than merely present. The `logs/` directory (created by the
  launchd plists) is gitignored and was never named in the brief.

## Pathway options

**Now** — fix or stabilize what exists:
- Nothing is broken. The one gap worth closing is `logs/health.log` rotation
  and a stated retention policy for the dashboard's verdict.

**Next** — highest-leverage addition given the current architecture:
- Turn the health check's six probes into the review's own baseline: the
  status review already re-runs most of them by hand, and `health_check.py`
  already owns them.

**Later** — needs a real architecture decision first:
- `PRAGMA user_version` schema versioning, and with it a decision to persist
  `ts_ms` so the calendar-day/timestamp invariant stops being implicit.
- What the comparison mechanism should group by beyond the plan code.

**Alternative direction** — a pivot worth naming, if one is genuinely on the
table:
- None. The brief's target is being met; a pivot would be a decision for an
  expansion review, not this one.
