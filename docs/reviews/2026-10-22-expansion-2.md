# Expansion Review — 2026-10-22

**Brief dated:** 2026-09-10 (last amended 2026-10-22)
**Last status review:** 2026-10-22 — 14 of 14 criteria verified
**Milestone that prompted this:** the brief's last open criterion went green
and the operational layer (self-check, backup, restore, schedule visibility)
landed the same day; this review asks what that taught, not whether it works.

## Headline

The target should not move. Building the service layer confirmed that this
project's remaining problems are operational — an unattended job that can be
wedged, a credential that can expire, a store that can be unopenable — not a
missing capability. The one thing the milestone did expose is a hole in a
criterion that only ever asked about hex literals: the shared chart template
still leaks named colours, which is exactly the class of thing the template
was built to end. That is the single amendment; everything else is parked as
implementation hardening or declined.

Two expansion review ran within hours of each other today. The earlier one
(2026-10-22-expansion.md) adopted five items and all five are implemented;
this one deliberately adopts almost nothing, because a target that moves twice
in a day cannot be graded.

## What building this taught us

**Assumptions that turned out wrong:**

- **Visual finish was not a per-chart problem.** Per-chart `update_layout`
  tuning never converged; the fix was one shared template, one palette, one
  theme. Both the title/legend collision and the "pretty good, not great"
  complaint trace to the same absence.
- **Concurrency was the real cost of the service layer.** A single shared
  `sqlite3.Connection` interleaved rows across threads, which surfaced as a
  `KeyError` in `load_runner_profile`; WAL plus a per-thread connection was
  the fix. Scheduling and Streamlit were the easy halves.

**Harder than expected, and why:**

- **Garmin auth across unattended runs.** The refresh (05:00) and the health
  check (06:30) both need the token, and a failure is visible only inside a
  log. The health check's own `stored-vs-garmin` probe can fail because of the
  credential rather than because of the data.
- **Recovering the store.** Schema versioning, a snapshot before every
  scheduled write and a restore path had to exist before the schedule could be
  trusted; the store is the only durable thing this project owns.
- Telling a *running* refresh from a *dead* one was the concrete symptom: the
  job's stdout was block-buffered to a file, so a wedged run and a finished run
  left the same trace. That is now solved (start marker + `launchctl` probe +
  a 30-minute wedge limit + a 26-hour staleness limit), and it is why the
  corresponding status-review flag dissolves below.

**Surprisingly easy, or came for free:**

- Nothing was reported here. The owner's assessment is that the remaining
  cheap capabilities (digests, exports, backtesting over the stored history)
  are not wanted, not that they are hard.

## Emergent capabilities

What now exists as a side effect that would have been a project of its own
before starting:

- **~3.5 years of Garmin history in a rectangular table** (911 activities,
  ~42k metric-series rows) reachable with one `sqlite3` query, no network.
  Backtesting a metric change against real history is now a script, not a
  fetch-and-parse project.
- **A hardened unattended path to Garmin** — owned HTTP layer with hard
  deadlines, persisted DI token, 1Password/env fallback, snapshot-before-write.
  Any future scheduled job over this data inherits it.
- **A self-checking service pattern** — `health_check.py` with nine probes, a
  sidebar verdict, launchd jobs for dashboard/refresh/health. A second
  scheduled job (a report, an alert) is now a plist and a script.

The owner explicitly wants none of the capabilities these enable (see the
out-of-scope line added below). Recorded because "cheap" is not the same as
"wanted".

## Adjacent problems noticed

Not this project's job, but visible now:

- **Garmin's token lifetime is an upstream property**, not something this
  project can fix; the response is a re-auth path, which is hardening.
- **macOS sleep/wake vs a 05:00 timer.** A Mac asleep at 05:00 runs the job on
  wake; launchd's catch-up behaviour is platform behaviour and no criterion
  should promise more than it does.
- **Streamlit's rerun model** already has a project-local answer (the
  store-fingerprint poll fragment); the general problem belongs to Streamlit.
- **The metric spec's §8 registry** is no longer drifted (it is now a key list
  with a machine check), but "is the registry a Garmin-field list or a
  metric-key list?" remains a question for the spec's own reader, not the
  brief.

## Amendments made to the brief

- **Objective:** unchanged. The target is still valid reports from the owner's
  own Garmin data, run locally as a self-refreshing service.
- **Criteria added:** none.
- **Criteria removed or replaced:** criterion 13 replaced — "no inline hex
  colour literals remain in `dashboard.py`" → "no colour literal, hex or CSS
  name, remains outside `chart_theme.py` (a `test_chart_theme.py` assertion
  fails on one)". The hex-only wording was satisfied while named colours
  bypassed the palette, so the criterion measured the wrong thing.
- **Is-done bar:** unchanged — still about data validity, not presentation.
- **Out of scope added:** scheduled digests, dataset exports, or a
  history-backtesting harness — declined because the owner reports none is
  worth having even now that the store and the launchd pattern make them
  cheap; revisit only if a concrete question appears.

No other criterion was invalidated. Criterion 14 (the service checks itself)
now also carries the schedule observability that criterion 11's review flag
asked for, so no wording change is needed there.
