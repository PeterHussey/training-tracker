# Status Review — 2026-10-22

**Reviewed against brief dated:** 2026-09-10 (amended 2026-10-20, 2026-10-22)
**Previous review:** 2026-10-21 (`docs/reviews/2026-10-21-status.md`)
**Cadence:** on schedule (weekly while active; the previous review was one day ago)

## Headline

All 14 criteria now have executed evidence behind them, up from 13 — the new
one (the service checks itself and the store is recoverable) is verified by a
green health check, a matching `PRAGMA user_version`, a snapshot written before
the last scheduled refresh, and a restore that reproduced the live store
exactly. The brief's target is met.

The useful part of this review is what the criteria do not cover. The scheduled
refresh is the only thing that keeps the data true, and its failure path is
invisible: a kickstart that never reached the project's code produced no log
line at all, and `check_refresh_schedule` would still have passed on a log
written by a job that no longer exists. A store written by a newer schema is
refused with a clear message, but the dashboard surfaces that refusal as a raw
traceback. The health check on a not-yet-installed clone reports seven failures
instead of "not set up yet". None of these is a criterion failure, and all of
them are one-line fixes.

  stated manual step; until that lands, the literal clause stays unexecuted.
  Also unprobeable: the platform's own launchd load state across a real login
  cycle (the plist's `RunAtLoad`/`KeepAlive` were read instead).

## Debt

- **The metric spec's §8 registry and the store's key names have drifted
  apart.** The spec lists 23 legacy flat names (copied verbatim from
  `garmin_fields.METRICS`) and calls them the registry; the store holds 68
  dotted keys, none of which matches a registry name, and 20 of them have no
  registry counterpart (`age_graded.pct`, `injury.max_run_ratio`,
  `fitness.vo2max`, `vdot.shape`, `marathon.shape_pct`, `pmc.*`, `load.acwr`).
  The health check compares family *prefixes*, so it cannot see this. Undoing
  it means deciding whether the registry is a Garmin-field list (as it says)
  or a metric-key list (as a reader will assume), then making the spec say so
  in one sentence and adding a key-level check. Flagged in the 2026-10-21
  review and still open.
- **Named colour literals still bypass the palette.** `dashboard.py` has no
  hex literals, but ten `add_hline`/`add_hrect` calls pass `"gray"`,
  `"lightgreen"`, `"orange"` and `"red"` directly. The criterion only asked
  about hex, so this is not a failure — it is a hole in the shared template.
- **WMA age factors clamp silently outside 30–110.** Age 29 is graded as 30
  and age 111 as 110, with no warning in the output.
- **`decoupling` is implemented but not emitted.** The spec says so (§2.3),
  the module and its tests exist, the dashboard shows "—". The criterion
  lists decoupling in the full metric set; the code is ready, the pipeline
  does not call it.
- **`health_check.py` assumes an installed clone.** It opens the store without
  creating `data/`, so on a fresh clone six checks fail with
  `OperationalError: unable to open database file` and a seventh with
  "no scheduled refresh log" — 7 failures for a machine that is simply not
  set up yet.

## Risk

- **A wedged scheduled refresh is invisible for up to 26 hours.** The job's
  stdout is block-buffered to a file, so a refresh that is still running (or
  one that dies before writing) leaves no trace in `logs/refresh.log`;
  `check_refresh_schedule` only looks at that file's mtime with a 26-hour
  tolerance, and passes on a log written by a job that no longer exists. A
  refresh was observed hung for 9m23s in an `open()` during interpreter
  startup — it never reached the Garmin fetch, and nothing said so. The data
  can silently be a day stale.
- **The launchd refresh has no wall-clock cap.** The brief's 90 s guard is a
  dashboard-refresh cap; the scheduled job's successful run today took 3m20s,
  and a hung one is unbounded.
- **The dashboard shows a raw traceback when the store cannot be opened.**
  `get_store()` has no `try/except`, so a store written by a newer schema (a
  clear `RuntimeError` from the store) or a missing `data/` directory reaches
  the user as a stack trace. The health check's own `7 check(s) failed` output
  shows the same assumption on a fresh clone.
- **The Garmin token can expire between refreshes.** The refresh and the
  health check both need it; a failure is visible only in the log, and the
  health check's `stored-vs-garmin` probe needs a live token too, so the
  check can fail because of the credential rather than because of the data.
- **The chart template is still unverified against unusual figure sizes.** The
  degenerate attack covers values, not sizes — a tall figure is what pushed
  the legend into the title once already. (Carried from 2026-10-21; the
  expansion review parked it.)

## Scope drift

- **Crept in despite being out of scope:** nothing found. The scheduled
  health check, the pre-write snapshot, the schema versioning and the log
  trimming all serve criteria in the brief.
- **Built without ever being decided:** nothing new. The one item still open
  is the §8 registry's status (debt above) — it was written as a
  Garmin-field list and has been read as a metric list ever since.

## Pathway options

**Now** — fix or stabilize what exists:
- Make a scheduled refresh visible while it runs: flush stdout (or write a
  start marker line), and have `check_refresh_schedule` ask launchd whether
  the job is loaded instead of trusting a log's mtime. One line each, and the
  invisible-staleness risk goes away.
- Catch the store-open failure in `dashboard.get_store()` and show the
  store's own message ("store schema v99 is newer than this code — update the
  app or restore an older backup") instead of a traceback.
- Let `health_check.py` say "not installed yet" (one check, one line) when
  `data/training.sqlite` does not exist, instead of seven failures.

**Next** — highest-leverage addition given the current architecture:
- Reconcile the metric registry: decide whether §8 is a Garmin-field list or a
  metric-key list, make the spec say which, and extend the health check from
  family prefixes to key sets so the answer is machine-checked.

**Later** — needs an architecture decision first:
- Give the launchd refresh the same wall-clock cap the dashboard has, and
  decide what the health check does about a job that is loaded but has been
  running for too long.
- Emit `load.decoupling` from the pipeline, or drop it from the criterion's
  metric list — the spec already says it is not emitted, so the brief and the
  spec disagree with each other.

**Alternative direction** — a pivot worth naming, if one is genuinely on the
table:
- None. The brief's target is met and the remaining work is operational
  hardening of the service layer, not a change of target.

## Flagged for expansion review

- Criterion 5's "metric definitions match `docs/v2/metrics-spec.md`" is
  ambiguous between the formulas (which match) and the registry key names
  (which do not). The wording could name which half it means.
- Criterion 11's "with no user action" is unobservable while a refresh is
  stuck: nothing in the system distinguishes a running job from a dead one.
  A staleness bound would make the criterion checkable.
- Criterion 8's fresh-clone clause does not say what the health check should
  do on a not-yet-installed clone — today it reports seven failures for a
  machine that has not been set up.
- Criterion 5 lists `decoupling` in the metric set while the spec's §2.3 says
  the pipeline does not emit it; one of the two should move.
